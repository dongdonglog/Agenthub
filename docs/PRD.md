## 1. 背景与问题

### 1.1 现场的真实流程

一线工程师遇到故障时，实际动作是：先在群里说两句现象，被追问后再去导日志/数据，把文件甩给 AI，等一会儿，补一句"再看下 error"，最后把结论整理成文档转发。**这不是一次问答，而是一段有状态的协作**。

### 1.2 前一代（AA）已经证明了什么

AA 验证了若干硬骨头：会话内串行、排队消息合并成批、投递幂等、崩溃恢复、表情/卡片只做投影。这些经验直接复用。

但也暴露了六个不满：

| # | 不满 | 具体表现 |
|---|---|---|
| 1 | **交互单薄** | 只有"表情 + 一张进度卡 + 一段文本"，不能收集参数、不能给按钮、不能确认 |
| 2 | **没有任务态** | 长任务只能干等；关掉飞书就找不到进度；不能查历史任务 |
| 3 | **不会用企业知识** | 不知道公司文档、历史故障、规范；每次都从零解释 |
| 4 | **模型与成本黑盒** | 不能按群/按人换模型；不知道谁花了多少 token |
| 5 | **单通道、难治理** | 只有钉钉；管理面弱；配额、审计、失败重投都缺 |
| 6 | **部署重** | Node + 每会话一个 agent 进程（约 100MB/会话），扩容靠加机器 |

### 1.3 为什么用 Go 重写

- 单二进制交付，容器镜像小，现场部署不需要 Node 工具链；
- goroutine 承载会话与并发，内存占用与进程数解耦；
- 静态类型 + 明确的模块边界，适合长期维护的可靠性系统；
- 生态成熟：pgx / sqlc / goose / River / templ / OpenTelemetry 都是一线方案。

## 2. 产品定位

### 2.1 一句话

**飞书里的团队 AI 工作台**：不只是"能回答"，而是"能把一件事做完并交付"。

### 2.2 差异化

| 维度 | 前一代 AA | AgentHub |
|---|---|---|
| 交互 | 表情 + 文本 + 一张进度卡 | 卡片即界面：参数收集、确认、结果卡、按钮追问 |
| 任务 | 无任务概念 | 任务模式：后台执行、进度可见、完成 @ 通知、`/tasks` |
| 知识 | 无 | 飞书云文档同步 + 混合检索；个人/团队记忆 |
| 工具 | 固定几个 | MCP 市场 + 内置工具 + 沙箱执行 |
| 模型 | 单模型 | 多模型路由，按群/按人覆盖，成本可见 |
| 治理 | 基础指标 | 管理台：会话回放、失败重投、配额、审计、成本 |
| 通道 | 钉钉 | 飞书优先，通道抽象预留钉钉/企微/Slack |
| 运行 | Node 多进程 | Go 单二进制 |

### 2.3 不做什么

- 不做通用 IM 客服工单系统（不替代飞书服务台）；
- 不做低代码工作流编排器（不替代 Dify/n8n）；
- v1 不做多租户 SaaS、不做跨企业 ISV 应用；
- 不追求"全自动替代人"——关键动作必须有人确认。

## 3. 用户与场景

### 3.1 角色

| 角色 | 诉求 | 使用方式 |
|---|---|---|
| 现场工程师 | 快速定位问题，少打字 | 私聊描述 + 传日志/数据，收到结论与下一步 |
| 研发/支持 | 反复追问、要证据、要报告 | 群里 @机器人，引用历史消息追问 |
| 团队负责人 | 知道团队在用什么、花了多少 | 管理台看用量、成本、失败率 |
| 运维 | 部署、排障、控权限 | 配置、健康检查、审计 |

### 3.2 三个核心故事

**故事 A：现场诊断**
> 工程师：「抓取时机械臂突然停了，没报 collision」→ 上传 `.mcap` → 「综合看一下」
>
> AgentHub：先回卡片「已收到 2 条消息 + 1 个文件，正在解析」→ 工具调用过程折叠展示 → 结果卡：故障摘要 / 3 条原因假设 / 每条的证据（时间、topic）/ 数据缺口 / 下一步动作 + 按钮「生成报告」「继续追问」。

**故事 B：周报生成**
> 负责人：「把本周群里讨论的 P0 问题整理成周报」→ 卡片弹出参数（时间范围、是否包含已关闭）→ 确认 → 后台任务执行 → 完成后 @ 他，附飞书文档链接。

**故事 C：研发问答**
> 新同事：「我们的发布流程是什么？」→ 机器人检索知识库（飞书文档）→ 回答并附 3 条来源链接 → 「继续问：回滚怎么做」沿用同一会话。

### 3.3 用户旅程（一条消息）

```
@机器人 ──▶ 状态表情/卡片首帧（<2s）──▶ 理解中 ──▶ 工具执行（折叠）──▶ 结果卡
                                              │
                                              └─ 缺参数 → 参数卡 → 用户提交 → 继续同一 Run
```

## 4. 目标与指标

### 4.1 北极星

**周活跃会话中"完成任务并产生交付物"的比例**（目标 ≥ 40%）。

### 4.2 指标

| 类别 | 指标 | 目标 |
|---|---|---|
| 体验 | 首帧卡片延迟 P95 | < 2s |
| 体验 | 完整回答 P95（不含模型排队） | < 30s |
| 可靠 | 消息丢失率 | 0（kill -9 验证） |
| 可靠 | 重复交付率 | 0 |
| 可靠 | 投递成功率 | ≥ 99.5% |
| 规模 | 单实例活跃会话 | ≥ 500 |
| 规模 | 单实例并发 Run | ≥ 50 |
| 成本 | 常驻内存（不含沙箱） | < 300MB |
| 成本 | 单次问答平均 token | 可观测，月度下降 20% |
| 质量 | 回答被追问"不对/重来"的比例 | < 10% |

## 6. 交互设计

### 6.1 进度卡（三段式）

```
┌──────────────────────────────────────┐
│ 🧠 正在分析 · #12                     │
│ ──────────────────────────────────── │
│ 已执行 2 次思考，3 次工具调用          │
│ ▸ 读取 现场数据.mcap（1.2s）           │
│ ▸ 查询 topic /error（0.8s）            │
│ 正在核对时间窗…                        │
│ ──────────────────────────────────── │
│                         [ 停止 ]      │
└──────────────────────────────────────┘
```

- 首帧在收到消息后 2 秒内出现（不等模型）；
- 工具步骤默认折叠，只显示最近 3 条；
- 终态：改为结果卡或失败卡，按钮禁用。

### 6.2 结果卡

```
┌──────────────────────────────────────┐
│ ✅ 分析完成 · #12                     │
│ 机械臂停止最可能是急停触发，其次…      │
│ ──────────────────────────────────── │
│ • 假设 1：…（证据：12:03:11 /error）   │
│ • 假设 2：…（证据：12:03:15 /state）   │
│ 数据缺口：缺少 12:02 之前的日志        │
│ 来源：现场数据.mcap · 故障手册 §3.2    │
│ [继续追问] [生成报告] [转交] [重试]    │
└──────────────────────────────────────┘
```

### 6.3 参数卡

当模型判断缺关键参数且无法从历史推断时，发参数卡：下拉/输入框/时间范围 + 「提交」「跳过」。提交后**继续同一 Run**，不新开。

### 6.4 任务模式

- 触发：用户说"后台跑"或任务预计 > 2 分钟；
- 行为：立即回执卡「已转后台」，完成后在原消息回复并 @ 发起人；
- `/tasks` 列出运行中与最近 20 条。

### 6.5 命令

| 命令 | 语义 |
|---|---|
| `/help` | 用法与示例 |
| `/status` | 当前阶段、排队数、模型 |
| `/stop` | 停止当前批次，保留队列 |
| `/clear` | 取消全部排队，不停止当前 |
| `/reset` | 停止 + 取消 + 换代 |
| `/tasks` | 我的任务 |
| `/model` | 查看/切换模型 |

### 6.6 文案与降级

- 失败必须说明"发生了什么 + 用户可以做什么"，不暴露堆栈；
- 卡片失败 → 文本；表情失败 → 静默；工具超时 → 说明并给重试按钮；
- 不出现内部 Run ID、文件路径、模型名（管理员视图除外）。

### 6.7 消息量控制

一次交互最多 1 张卡 + 1 条结果（多条结果合并到卡片或按序追加）；排队、取消、重试都不额外发文本。

## 7. 飞书能力依赖

详见 [feishu-capabilities.md](feishu-capabilities.md)。关键结论：

- 长连接 3 秒内必须确认，且为**集群模式**（多实例时只有一个实例收到事件）；
- 群消息默认需要 @机器人；读取全部群消息需管理员审批 `im:message.group_msg`；
- 卡片按钮回调依赖 `card.action.trigger` 与 V2 卡片结构，**长连接是否支持待实测**；
- 机器人只能删除自己添加的 reaction，且删除建议按 emoji 而非 id；
- 文件大小、文本长度、卡片更新频率上限均需实测后写死配置。

## 8. 非功能需求

### 8.1 性能

- 单实例 500 活跃会话、50 并发 Run；
- 首帧 P95 < 2s；ACK 3s 内 100%；
- 大文件流式处理，常驻内存不随文件线性增长。

### 8.2 可靠性（不变量）

| 编号 | 不变量 |
|---|---|
| I1 | 同一会话最多一个非终态 Run（数据库唯一索引保证） |
| I2 | 批次输入创建后不可变 |
| I3 | 先落库、后确认 |
| I4 | 终态与投递记录同事务写入 |
| I5 | 投影失败不回写业务状态 |
| I6 | 迟到事件按 run_id 丢弃 |

### 8.3 安全

- 工具在容器沙箱执行：只读挂载、无宿主 socket、egress 白名单、CPU/内存/磁盘限额；
- 密钥只从环境变量读取，日志与归档不落明文；
- 附件名、内容一律视为不可信输入；
- 管理面无默认口令，必须前置网关或 OIDC。

### 8.4 成本

- 按会话/用户/模型记录 token 与费用；
- 支持小模型分流（分类、摘要）与大模型兜底；
- 批次合并减少重复上下文。

### 8.5 合规

- 数据保留期可配（附件 30 天、会话 1 年）；
- 支持按用户删除会话与记忆；
- 外发模型需显式配置与授权。

## 10. 配置与部署（摘要）

- 健康检查与指标只监听回环，管理面单独端口；

## 12. 风险与开放问题

| 风险 | 影响 | 应对 |
|---|---|---|
| 长连接不支持卡片回调 | 停止按钮方案变化 | M1 第一周 Spike；备选 webhook 或 `/stop` |
| 群消息权限审批慢 | 群聊只能 @ 触发 | 提前申请；按"需 @"设计 |
| 文件/文本上限未知 | 分块与交付参数需调整 | 实测后回填配置 |
| Go agent 生态弱 | 工具调用需自研 | 薄 loop + MCP；先跑稳单轮 |
| 沙箱成本 | 部署门槛上升 | 容器 + 只读挂载起步，gVisor 可选 |

**开放问题**

1. v1 是否默认"批次合并"，还是逐条处理（更自然但更贵）？
2. 任务模式是否进 v1（影响 M3 范围）？
3. 是否需要私有化部署（影响模型接入方式）？
4. 知识库首期是否只接飞书云文档？
5. 管理台是否需要多用户与角色？
